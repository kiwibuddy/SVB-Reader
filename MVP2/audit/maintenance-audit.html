Blocking — stops a release

B1
iOS blockerDeadline passed

SDK 53 cannot compile against the iOS 26 SDK

Apple's minimum-SDK rule took effect 28 April 2026: every iOS upload must be built with the iOS 26 SDK (Xcode 26) or later. This raises the build SDK only — your deploymentTarget of 15.1 can stay, so no users get dropped. Expo SDK 54 was the first release to build on that toolchain. There is no partial fix and no extension available.

B2
Android blocker23 days

The app targets API 34, and Google Play's next gate is API 36

app.json:91 — expo-build-properties pins targetSdkVersion: 34 and compileSdkVersion: 34, which is a deliberate downgrade from SDK 53's own default of 35. Two consequences, one already active. Since 31 August 2025, apps below API 35 stop being discoverable to new users on newer Android devices — existing installs keep working, but your Play listing has likely been invisible to a growing share of new users for a year. And from 31 August 2026, Play rejects any update below API 36 outright. An extension to 1 November 2026 can be requested if you need it.

The decision that governs the upgrade

This is the item to settle before touching a version number. It is the main thing that changed between revision 1 of this report and this one.

D1
Decide first

The native projects are committed, so this is no longer a managed Expo app

ios/SourceViewTogether.xcodeproj, a Podfile, and a full android/ Gradle project are all in git. That means npx expo install alone will not upgrade you — the native projects hold their own copies of the build settings and won't move on their own. You have two routes, and they differ enormously in cost:

Return to managed (recommended). Delete ios/ and android/ and let expo prebuild regenerate them from app.json on every build. Every future SDK upgrade becomes a one-line version bump. Viable only if the native projects contain no hand-edits — they look prebuild-generated, but that must be verified before deleting anything.

Stay bare. Hand-migrate the Xcode project, Podfile, Gradle files and manifests across four SDK versions. This is the expensive path and buys you nothing unless you have native customisations worth keeping.

Breaks on upgrade

U1
Visual regression

Android edge-to-edge is explicitly switched off, and SDK 54 removes the switch

android/gradle.properties:59 sets expo.edgeToEdgeEnabled=false. SDK 54 makes edge-to-edge mandatory and deletes that opt-out, so content will draw beneath the system bars whether or not the layouts expect it. Screens that currently assume the system reserves that space will shift. This is the most likely source of visible breakage after the bump.

U2
Needs work

Reanimated 4 moves its core into a separate package

v4 is New-Arch-only — which you already satisfy — but relocates its runtime into react-native-worklets, installed alongside and registered in the Babel config. Configuration work rather than rewriting animations.

U3
Visual regressionNeeds a device

Liquid Glass re-skins system chrome as soon as you build on iOS 26

Compiling against the iOS 26 SDK opts you into the new material for navigation bars, tab bars and sheets — not deferrable. This app uses a custom header and a BlurView tab background, which interact with it directly. A simulator understates this; budget a pass on real hardware.

U4
Deprecated API

One screen still imports SafeAreaView from react-native

app/(tabs)/[segment]/index.tsx:4 — deprecated since RN 0.81 and scheduled for removal. react-native-safe-area-context 5.4.0 is already a dependency and used correctly elsewhere, so this is a one-line change.

Resolved — expected problems that aren't

Worth stating explicitly, because these are the findings that usually make an upgrade of this size look frightening, and this branch has already dealt with all of them.

R1
Free

expo-av is dead weight, not a migration

The SDK 55 removal of expo-av is normally the headline cost of this upgrade. Here, nothing imports it — no Video, no Audio.Sound, anywhere in the app. It sits in package.json and in the plugins array purely as residue, and so does expo-video. Delete both dependencies and both plugin entries; there is no migration to perform.

R2
Already done

New Architecture is on everywhere

newArchEnabled: true in app.json and newArchEnabled=true in android/gradle.properties:38, with Hermes enabled. The legacy architecture was dropped in SDK 55, and that would have been the single most expensive item on this list.

R3
Already done

The dependency manifest is clean

No deprecated @types/react-native, no legacy expo-cli, no committed dist/, and expo-haptics properly declared — all of which are wrong on main and right here. React 19.0.0 and RN 0.79.6 are correctly matched to SDK 53.

Latent

L1
Ambiguous state

Three files disagree about which build you shipped

app.json says version 1.2.1 / build 20 / versionCode 20. But ios/SourceViewTogether/Info.plist says 19, and android/app/build.gradle:95 says versionCode 19. With native directories committed and eas.json set to appVersionSource: "local", the native values win — so the commit labelled "Testflight v1.2.1 (Build 20)" most likely produced a binary stamped 19. Check what TestFlight actually received before assuming your build numbers are where you think they are.

L2
Fragile

Three packages are imported but never declared

@react-navigation/bottom-tabs, @react-navigation/elements, and expo-file-system — the last used in earnest by services/BibleStorageManager.ts and services/QuestionsLoader.ts, both core to loading Bible content. They resolve today only via hoisting. Declare them before upgrading, so a real break is distinguishable from a resolution artefact.

L3
Dead code

A commented-out import references a package Expo has removed

app/(tabs)/Home.tsx:17 still carries // import { BarCodeScanner } from 'expo-barcode-scanner'. The package was removed from Expo, and QR scanning has correctly moved to expo-camera. Harmless, but it will read as a live dependency to the next person who greps for it.

L4
OTA risk

runtimeVersion is a hardcoded string

runtimeVersion: "1.2.1" with updates set to ON_LOAD. Because it is pinned rather than derived by policy, it will not move when you change native code — and an over-the-air update built against SDK 57 delivered to a binary built on SDK 53 crashes on launch. This must be changed as part of the upgrade, not after it.

Hygiene

H1
Repo weight

100 MB of source Bibles live at the repo root

FRA-Bible.json (50 MB) and FRA-Bible-with-questions.json (50 MB) are committed at top level and imported by no application code — they are inputs to the scripts in scripts/, not app assets. Every clone pays for them forever. Move them out of git, or into a release asset.

H2
App size

25 MB of JSON ships inside the binary

assets/data/ totals 25 MB, dominated by newBibleNLT1.json (15 MB) and verseIndex.json (6.4 MB), parsed as JSON at runtime. That is real download size and real startup cost on low-end devices. You already have expo-sqlite and a substantial database layer — moving the bulk text there would pay off on both counts, though it is a project rather than a fix.

H3
Cruft

Backups and build output are tracked

backup_code/, dist-android/, api/sqlite.ts.backup, and a committed sourceview.db. None should be in version control; the .backup file in particular shadows the real module in searches.

H4
Config

The URL scheme is still the template default

scheme: "myapp". Deep links resolve as myapp:// — unbranded, and liable to collide with any other app that also never changed it. Worth fixing while you are in app.json anyway.

H5
Docs

The release notes are dated a year early

RELEASE_NOTES_1.2.1.md reads "Release Date: January 2025", but the commits behind that build run October–November 2025. Worth correcting — a wrong date in the one document you'd consult later is how a repo becomes hard to trust.

H6
Process

main is 156 commits behind the app

Every branch in the repo except this one sits on the abandoned pre-rebrand codebase, and main is among them. It is why this report had to be written twice. Merge Nov-New-Build- into main so the default branch is the app again.

Recommended order

Steps 1–3 are safe on SDK 53 and should be verified working before any version changes — go into the upgrade with a clean baseline so the first red build means something. Step 2 is the fork in the road.

  1. Reconcile versions and the manifest

    Settle the 19-vs-20 discrepancy against what TestFlight actually holds, declare the three undeclared packages, drop expo-av and expo-video from both dependencies and plugins, and delete the dead barcode-scanner comment. L1, L2, L3, R1

    npx expo install @react-navigation/bottom-tabs \
  @react-navigation/elements expo-file-system
npm uninstall expo-av expo-video   # nothing imports either

  2. Decide managed vs bare — then commit to it

    Diff ios/ and android/ against a fresh expo prebuild --clean on SDK 53. If nothing meaningful differs, delete both directories and return to managed; every later step gets dramatically cheaper. If real hand-edits exist, document them now, because you will be re-applying them by hand. D1

  3. Merge the branch back into main

    Nov-New-Build- is a strict descendant of main, so this is a fast-forward with no conflicts. Do it before the upgrade, so the SDK work has an ordinary branch to land on. H6

  4. Upgrade to SDK 57

    Straight across rather than one SDK at a time. SDK 56→57 and RN 0.85→0.86 carry no breaking changes, so the real work sits at the 53→54 and 54→55 boundaries regardless of how many steps you take getting there. Raise targetSdkVersion and compileSdkVersion to 36 in the same pass. B1, B2

    npx expo install expo@^57.0.0
npx expo install --fix
npx expo-doctor

  5. Clear the fallout

    Add react-native-worklets and update Babel for Reanimated 4; rework layouts for mandatory Android edge-to-edge; move the last SafeAreaView import across; set runtimeVersion deliberately before any build that could receive an OTA update. Expect this step, not step 4, to consume the time. U1, U2, U4, L4

  6. Build and test on real hardware, both platforms

    An iOS 26 device for Liquid Glass against the custom header and blurred tab bar, and an Android 16 device for edge-to-edge. Walk the full reading flow in both English and French — the localisation is the newest and least-exercised code in the app. U1, U3

What this review did not cover

Static review of committed source only — nothing was installed, compiled, or run. Still open:

  • Whether the app builds today. No npm install, no type check, no bundle — a compile will likely surface more than this list.
  • Whether ios/ and android/ contain hand-edits. This is the step-2 decision and it needs a real prebuild diff to answer.
  • What TestFlight actually holds, and whether the live App Store listing matches com.sourceview.together. Both need the consoles.
  • The database layer — seven modules including migrations — and how it behaves across an app update with an existing user database.
  • Correctness of the French translations. I confirmed the plumbing is wired up, not that the content is right.
  • Apple's privacy-manifest requirements for your dependency set once you are building on SDK 57.
